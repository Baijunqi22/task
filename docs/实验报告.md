# 实验：处理机调度与死锁

## 一、实验目的

1. 理解处理机调度和死锁的基本概念，掌握处理机调度与避免死锁的基本工作原理；
2. 用 C 语言编程模拟实现**先来先服务（FCFS）**调度算法；
3. 用 C 语言编程模拟实现**多级反馈队列（MLFQ）**调度算法；
4. 用 C 语言编程模拟实现**银行家算法**，掌握死锁避免的基本方法；
5. 通过对周转时间、带权周转时间、等待时间、响应时间以及安全序列的计算与比较，
   加深对进程调度与死锁避免理论知识的理解。

## 三、实验原理

### 3.1 处理机调度

处理机调度是操作系统在多道程序环境下，按照一定的算法把处理机分配给就绪进程的过程。
在单处理机系统中，任一时刻只有一个进程能够占用处理机，因此需要解决“谁先运行、
运行多久、何时被剥夺”的问题。常用的调度算法分为非抢占式（FCFS、SJF 等）与抢占式
（时间片轮转、多级反馈队列、抢占式优先级等）两大类。

### 3.2 评价指标

设进程 `i` 的到达时间为 `T_arrive`、服务时间为 `T_service`、开始时间为 `T_start`、
完成时间为 `T_finish`，则：

* 周转时间：`T_turnaround = T_finish - T_arrive`
* 带权周转时间：`W = T_turnaround / T_service`
* 等待时间：`T_wait = T_turnaround - T_service`（本实验中同时精确统计进程在就绪队列中停留的时间）
* 响应时间：`T_response = T_start - T_arrive`

一种调度算法的优劣通常用上述指标的平均值来衡量，其中**平均带权周转时间**最能反映
用户对系统“相对等待”的感受。

### 3.3 四种算法的原理

**（1）先来先服务 FCFS。** 按进程进入就绪队列的先后次序调度，非抢占，进程一旦占用
处理机便运行到完毕。算法简单、公平（对“先到者”公平），但不利于短作业：排在长作业
之后的短作业要等待很久，因而平均带权周转时间偏大；同时 FCFS 不会引起饥饿。

**（2）时间片轮转 RR。** 就绪进程按 FIFO 排成队列，队首进程运行一个时间片，时间片
用完仍未完成则剥夺处理机并排到队尾。时间片足够小时，所有进程都能在可接受的时间内
获得响应，系统对各进程“公平”；缺点是进程切换频繁，系统开销增大。时间片 q 过大时
算法退化为 FCFS；q 过小时则切换开销过大。

**（3）多级反馈队列 MLFQ。** 设置 N 个优先级递减的就绪队列，第 i 级队列的时间片为
基准时间片 × 2^(i-1)。新进程进入第 1 级队列；只有前面各级队列都为空时才调度第 i 级
队列；进程用完第 i 级队列的时间片仍未完成就降入第 i+1 级队列；更高优先级队列中有
进程到达时立即抢占；进程因 I/O 让出处理机，I/O 完成后又回到第 1 级队列（“反馈”）。
MLFQ 使短作业（含交互型作业）能在高优先级队列中迅速完成，同时让长作业在低级队列中
以较大时间片运行，兼顾了响应时间与系统吞吐量；其不足是长作业可能长时间得不到处理机
（饥饿），可以用“老化”策略缓解。

**（4）银行家算法。** 该算法通过在分配资源前进行**安全性检查**来避免系统进入不安全
状态，从而避免死锁。设 `Need[i][j] = Max[i][j] - Allocation[i][j]`：

* 安全性算法：令 `Work = Available`，反复在系统中寻找满足 `Need[i] ≤ Work` 且未完成
  的进程 i，若能找到则令 `Work = Work + Allocation[i]`、`Finish[i] = true`，
  表示进程 i 可以顺利执行完并归还其占用的资源；若所有进程都能完成，则系统处于
  **安全状态**，得到的进程次序就是一个**安全序列**。
* 资源请求算法：进程 i 提出请求 `Request` 时依次检查
  ① `Request ≤ Need[i]`（否则请求超过它声明的最大需求，属于非法请求）；
  ② `Request ≤ Available`（否则可用资源不足，请求不能立即满足，进程等待）；
  ③ 进行**试探性分配**并执行安全性算法，若分配后系统仍然安全则正式分配，
  否则撤销本次试探性分配，让进程等待。

需要强调的是：**不安全状态并不等于死锁**，它只是说明“系统可能进入死锁状态”。
银行家算法宁可让进程等待，也不让系统进入不安全状态。

### 4.2 进程控制块

```c
typedef struct {
    int    pid;             /* 进程编号 */
    char   name[NAME_LEN];  /* 进程名 */
    int    arrive;          /* 到达时间 */
    int    burst;           /* 需要占用处理机的总时间 */
    int    io_after;        /* 已占用 CPU 多少时间后请求 I/O，0 表示无 I/O */
    int    io_time;         /* I/O 持续时间 */

    int    finish;          /* 完成时间 */

    double w_turnaround;    /* 带权周转时间 */
    int    wait;            /* 等待时间 */
} Proc;
```

### 4.3 事件驱动的模拟方法与时间推进约定

调度类程序采用“时间按整数单位推进 + 事件驱动”的模拟方式：每一时刻先处理该时刻发生的
事件，再决定由哪个进程占用处理机运行一个时间单位。为了保证结果可复现，程序统一约定
同一时刻的事件处理次序为：

> ① I/O 完成唤醒 → ② 新到达进程入队 → ③ 老化提升 → ④ 抢占判断 →
> ⑤ 处理当前进程的“完成 / 请求 I/O / 时间片用完重新入队”

也就是说，同一时刻到达的新进程排在刚被剥夺处理机的进程之前；被抢占的进程回到它当前
所在队列的队尾，时间片重新计时（这符合“剥夺后重新排队”的教材描述）。

程序同时输出**甘特图**、**执行时间片段表**和**事件时间线**，便于对照算法规则检查每一步
调度是否合理。以 `test/mlfq_1.txt` 为例，第 2 个时间单位 P2 到达时立即抢占了正在第 2 级
队列中运行的 P1：

```
2        P2 到达（需占用 CPU 4），进入第 1 级队列队尾
2        P1（第 2 级队列）被更高优先级队列的进程抢占，回到本队列队尾
2        P2 获得处理机：第 1 级队列，时间片 1
```

### 4.4 各程序的实现要点

* **FCFS**：按到达时间稳定排序后依次执行；若下一个进程尚未到达，则记录一段“空闲”
  时间后再开始运行它。
* **RR**：用环形队列实现就绪队列；进程请求 I/O 时进入阻塞队列，I/O 完成后回到就绪
  队尾；处理机空闲（就绪队列为空但仍有阻塞进程）时，时钟直接跳到下一个事件时刻。
* **MLFQ**：为每一级队列各维护一个环形队列，并用 `level[]` 记录进程当前所在队列；
  通过“最高优先级非空队列”函数实现“前面各级队列均空才调度第 i 级队列”；老化周期
  到达时把所有就绪进程提升到第 1 级队列。程序还统计了每级队列的调度次数、累计运行时间
  以及每个进程在各队列上获得的处理机时间，便于分析算法的行为。
* **银行家算法**：输入支持“教材示例数据”“手工输入”和“文件读入”三种方式；文件采用
  `M/N/AVAILABLE/ALLOCATION/MAX/REQUEST` 关键字格式，程序会自动推断进程名与进程数，
  并校验 `Allocation ≤ Max` 等约束。批处理模式（`-b`）会依次执行文件中的请求并打印
  每一步的安全性算法表格，便于与手工计算核对。

### 5.3 多级反馈队列（MLFQ）

**测试 1**（`test/mlfq_1.txt`：P1(0,6)、P2(2,4)、P3(5,2)、P4(8,1)，3 级队列、基准时间片 1）

```
甘特图：| P1(Q1):0-1 | P1(Q2):1-2 | P2(Q1):2-3 | P1(Q2):3-5 | P3(Q1):5-6 |
         P2(Q2):6-8 | P4(Q1):8-9 | P3(Q2):9-10 | P1(Q3):10-12 | P2(Q3):12-13 |

进程名  到达时间  服务时间  开始时间  完成时间  周转时间  带权周转时间  等待时间  响应时间
P1      0         6         0         12        12        2.00          6         0
P2      2         4         2         13        11        2.75          7         0
P3      5         2         5         10        5         2.50          3         0
P4      8         1         8         9         1         1.00          0         0

平均周转时间 = 7.25，平均带权周转时间 = 2.06，平均等待时间 = 4.00
```

`(Q1)`、`(Q2)`、`(Q3)` 表示该片段中进程所在队列的级数。可以看出：

* P1 从第 1 级队列被逐级下放到第 3 级队列，时间片由 1 增加到 4；
* P4（服务时间只有 1）到达后立刻在第 1 级队列中完成，周转时间只有 1，响应时间为 0；
* P2 到达时正在运行第 2 级队列中进程的 P1 被立即抢占，体现了 MLFQ 对高优先级队列的照顾。

**测试 2**（`test/mlfq_2.txt`：P1(0,8, I/O 3+4)、P2(0,4)、P3(1,3)）

```
9        P1 的 I/O 完成，返回第 1 级队列队尾（反馈）
9        P3 运行完毕，撤销（周转时间 8）
9        P1 获得处理机：第 1 级队列，时间片 1
...
P1  8 个时间单位在各级队列上的运行时间：第 1 级 2、第 2 级 4、第 3 级 2
平均周转时间 = 12.00，平均带权周转时间 = 2.60
```

P1 请求 I/O 时已经降到第 2 级队列，但 I/O 完成后（9 时刻）又回到了第 1 级队列，
这正是“反馈”的含义：交互型进程重新变为高优先级，从而获得快速响应。

**测试 3（老化策略的效果）**（`test/mlfq_3.txt`：P1(0,20) 与 P2~P6 各为 (0,1)）

| 运行方式 | P1 在各队列上获得的处理机时间（第1级/第2级/第3级） | P1 周转时间 | 平均周转时间 |
| --- | --- | --- | --- |
| `mlfq -f test\mlfq_3.txt`（关闭老化） | 1 / 2 / 17 | 25 | 7.50 |
| `mlfq -f test\mlfq_3.txt -a 5`（每 5 个时间单位老化一次） | 2 / 2 / 16 | 25 | 7.50 |

启用老化后，事件时间线中出现了“老化：P1 等待时间过长，被提升到第 1 级队列”的记录，
长作业在高级队列中多获得了 1 个时间单位的处理机。本例作业个数有限，所以平均周转时间
没有变化；但老化机制的重要意义在于：当短作业源源不断到达时，它可以保证长作业不会
无限期地等待下去，从而避免饥饿。

### 5.4 同一组作业在三种算法下的对比

作业集：P1(0,5)、P2(0,3)、P3(0,1)（同时到达）。

| 算法 | 甘特图 | 平均周转时间 | 平均带权周转时间 | 平均等待时间 |
| --- | --- | --- | --- | --- |
| FCFS | `P1:0-5｜P2:5-8｜P3:8-9` | 7.33 | 4.22 | 4.33 |
| RR（q = 1） | `P1:0-1｜P2:1-2｜P3:2-3｜P1:3-4｜P2:4-5｜P1:5-6｜P2:6-7｜P1:7-8｜P1:8-9` | 6.33 | 2.38 | 3.33 |
| MLFQ（3 级，基准时间片 1） | `P1(Q1):0-1｜P2(Q1):1-2｜P3(Q1):2-3｜P1(Q2):3-5｜P2(Q2):5-7｜P1(Q3):7-9` | 6.33 | 2.38 | 3.33 |

三个进程的周转时间（P1/P2/P3）：FCFS 为 5/8/9，RR 与 MLFQ 均为 9/7/3。

分析：

1. 最短作业 P3 在 RR 与 MLFQ 下的周转时间由 FCFS 的 9 降为 3，**带权周转时间由 9.00
   降到 3.00**，说明按时间片公平轮转确实改善了短作业的处境；
2. 本例中 RR 与 MLFQ 的平均指标相同，但两者的过程并不一样：MLFQ 让 P3 在做完第 1 个
   时间片后仍以较高的第 1 级队列优先级先于 P1、P2 完成，同时把长作业 P1 下放到第 3 级
   队列（时间片放大到 4），从而减少了切换次数——

   ```
   MLFQ 各队列使用情况：第 1 级队列 时间片 1，被调度 3 次，累计运行 3
                        第 2 级队列 时间片 2，被调度 2 次，累计运行 4
                        第 3 级队列 时间片 4，被调度 1 次，累计运行 2
   ```

   也就是说，MLFQ 用“高级队列小时间片保证响应、低级队列大时间片减少切换”的方式，
   同时照顾了响应时间和系统开销，这正是它被实际系统广泛采用的原因。

### 5.5 银行家算法

**测试 1：教材经典例题**（`test/banker_1.txt`，5 个进程、3 类资源，`Available = (3 3 2)`）

初始状态的安全性检查结果：

```
步骤  进程   Work 可用资源   Need 尚需资源   Work+Allocation   Finish
1     P1     3 3 2           1 2 2           5 3 2             true
2     P3     5 3 2           0 1 1           7 4 3             true
3     P0     7 4 3           7 4 3           7 5 3             true
4     P2     7 5 3           6 0 0           10 5 5            true
5     P4     10 5 5          4 3 1           10 5 7            true

结论：存在安全序列，系统处于安全状态。安全序列为 P1 -> P3 -> P0 -> P2 -> P4
```

随后依次处理三个资源请求，正好演示了三种不同的判断结果：

| --- | --- | --- | --- | --- | --- |
| 1 | P1 请求 (1 0 2) | 满足 | 满足 | 分配后仍安全（安全序列 P1→P3→P0→P2→P4） | **分配成功** |
| 2 | P4 请求 (3 3 0) | 满足 | 不满足（A 类资源只有 2） | 未进行 | **资源不足，进程等待** |

## 六、结果分析

1. **FCFS 的公平是对“先到者”的公平。** 从 5.1 的测试 2 可以看出，短作业 P3 的带权
   周转时间达到 9.00，而长作业 P1 只有 1.00。FCFS 平均带权周转时间明显偏大，但实现
   最简单，且不会产生饥饿。
2. **时间片轮转以公平换响应。** 在 5.2 的测试 1 中，三个进程的响应时间为 0、1、2，
   而 FCFS 下后两个进程分别是 5 和 8。平均带权周转时间也从 4.22 降到 2.38。
   需要注意的是，q 的取值很关键：q 太大会退化为 FCFS，q 太小则切换频繁、开销增大。
3. **多级反馈队列兼顾了响应与开销。** 短作业在第 1 级队列中很快完成；长作业被逐级
   下放，在低级队列中用更大的时间片运行，减少了切换次数（见 5.4 的队列统计）。
   它的“反馈”机制使 I/O 频繁的交互型进程总能回到高优先级队列（5.3 测试 2）。
   其代价是实现复杂，且长作业可能饥饿，需要用老化策略缓解（5.3 测试 3）。
4. **银行家算法把“是否安全”作为分配资源的前置条件。** 5.5 的四个测试覆盖了全部
   分支：非法请求、资源不足、分配后安全、分配后不安全。特别要注意：
   `Request ≤ Need` 且 `Request ≤ Available` 只是必要条件，还必须通过安全性检查；
   而“不安全状态”并不等于死锁，只是存在发生死锁的可能。
5. **调度算法的选择取决于系统目标。** 批处理系统更关心吞吐量与平均周转时间，
   常采用 FCFS、SJF 及其变种；分时系统更关心响应时间与公平性，常采用时间片轮转；
   通用操作系统多采用多级反馈队列这类混合策略。

## 七、调试记录（实验过程中发现并解决的问题）

1. **同一时刻的事件次序会影响结果。** 一开始把“新到达进程入队”放在“时间片用完重新
   入队”之后，导致同一时刻到达的进程反而排在刚被剥夺的进程之后。查阅教材后统一改为
   “先处理到达（以及 I/O 完成），再处理被剥夺的进程”，并在文档中明确写出这一约定，
   保证结果可复现。
2. **`cur` 未初始化导致死循环。** MLFQ 模拟中表示“当前正在运行的进程”的变量用 `-1`
   表示空闲，但初始化时只做了 `memset(..., 0, ...)`，于是第 0 号进程被“假定”成正在
   运行，而它同时又留在就绪队列里，造成同一个进程出现两份、并且反复运行而永远无法
   完成，程序陷入死循环。用输出的事件时间线定位后，显式加入 `s.cur = -1;`，
   并把完成条件由 `rem[i] == 0` 放宽为 `rem[i] <= 0` 作为保护。
3. **进程始终没有“开始时间”。** 最初只在 FCFS 中记录了 `first_start`，导致 MLFQ 的
   统计表里开始时间与响应时间都是 `-1`。在“进程获得处理机”处补上记录后，四个程序
   的响应时间统计口径才完全一致。
4. **输入文件被解析器破坏。** 读文件时先对整行做了分词试探，再调用解析函数，结果分词
   时写入的 `'\0'` 把原行截断了，错误提示只显示“A”。改为用副本试探字段个数，
   既保证解析正确，也保证了错误信息能原样输出。
5. **银行家算法文件中请求段找不到进程。** 进程数 `n` 原来是在所有数据段解析完之后才
   赋给结构体的，而 `REQUEST` 段中按进程名查找时需要用到它，于是查找总失败。把
   `m`、`n` 的确定提前到第一遍扫描之后，问题消失。

## 八、思考题

**1. 时间片大小的选择对时间片轮转算法的性能有什么影响？**
时间片是 RR 的核心参数。时间片过大时，一个时间片足以让大多数进程运行完毕，算法退化
为 FCFS，短作业的响应时间变差；时间片过小时，进程切换次数急剧增加，用于进程切换的
开销（保存/恢复现场、队列维护等）在总开销中的比例上升。一般希望时间片略大于一次
典型交互所需的时间，并使切换开销控制在可接受的比例（如 10% 以内）。

**2. FCFS 与时间片轮转算法在“公平性”上有何不同？**
FCFS 的公平是“按到达次序服务”的公平：先到者先服务，长作业也不会被剥夺，但排在长作业
后面的短作业要等待很久。RR 的公平是“按时间片轮流服务”的公平：每个进程在一个时间片
结束时就可能被剥夺，任何进程都不会因为“自己的作业长”而无限期地挡住别人。因此 RR 的
响应时间更均匀，而 FCFS 的实现更简单。

**3. 多级反馈队列为什么要把时间片逐级加倍？**
高优先级队列中的进程通常是短作业或交互型进程，用小时间片可以让它们迅速获得响应；
而进入低级队列的进程往往已经表现出“长作业”的特征，若仍用小时间片，会带来大量切换
开销。让时间片随队列级数加倍，可以在保证响应时间的同时减少低级队列的切换次数，
兼顾系统吞吐量。

**4. 银行家算法为什么能避免死锁？不安全状态是否就是死锁状态？**
银行家算法在分配资源之前先判断分配后系统是否处于安全状态：只要存在安全序列，就一定能
按某个次序让所有进程都获得所需资源并顺利结束，因而不会发生死锁。若分配后系统变成
不安全状态，则予以撤销、让进程等待，使系统始终保持安全状态。需要注意，不安全状态只是
“可能”发生死锁——系统进入不安全状态后，若各进程后续的请求恰好按“安全”的方式推进，
仍然可能顺利完成；反之，死锁一定发生在不安全状态之中。所以安全状态是死锁状态集合的
补集中的一个子集。

**5. RR 与 MLFQ 在 5.4 的测试中平均指标相同，为什么仍说 MLFQ 更优？**
平均指标相同只是本例（3 个短作业、同时到达）的巧合。MLFQ 的优势在于它同时照顾了
两类作业：短作业在第 1 级队列中一次运行完；长作业被下放到低级队列，用更大的时间片
运行，切换次数更少。若作业集合中包含服务时间差别很大的作业，MLFQ 的“响应快 +
切换少”的优势就会体现在平均带权周转时间和系统开销上。此外，MLFQ 还能通过反馈机制
优先照顾 I/O 频繁的交互型进程。

## 九、实验总结

本次实验用 C 语言完成了 FCFS、时间片轮转、多级反馈队列三种处理机调度算法和银行家算法
的模拟。通过把“就绪队列如何组织、时间片如何推进、进程何时被剥夺或降级”这些规则写成
可执行的代码，并结合甘特图、事件时间线和安全性算法表格逐条核对，我对课本上的概念有了
更具体的认识：

* 调度算法的差别最终体现在周转时间、带权周转时间、等待时间和响应时间这些可量化的
  指标上，而这些指标可以通过模拟精确计算出来；
* “同一时刻该先处理什么事件”这样的细节同样会改变调度结果，因此必须明确约定算法规则
  并保持实现一致；
* 死锁避免与死锁检测不同，银行家算法以安全性检查为前提“防患于未然”，
  它以牺牲一定的资源利用率为代价换取系统的安全。

程序设计方面也有不少收获：把公共的输入解析、统计输出抽成公共模块后，四个程序的风格
一致、便于对比；事件驱动的模拟配合详尽的时间线输出，让调试调度逻辑变得非常直观。
